About Virasat & Viva Guide

A clean, robust full-stack heritage exploration prototype built using pure HTML5, CSS3, vanilla JavaScript, and a lightweight Node.js/Express backend.

Quick Jump: 🎯 Project Vision 💻 Technology Stack 🏗️ Architecture Diagram 🎓 Viva Defense Q&A (10 Questions)

🎯 Project Vision & Problem Statement

India possesses one of the world's richest civilizational heritages, featuring thousands of UNESCO World Heritage sites, historic forts, rock-cut temples, and majestic royal palaces. However, standard educational textbooks and tourist websites offer static, two-dimensional reading experiences that fail to inspire modern students or capture architectural depth.

Virasat was conceived as a digital heritage preservation platform and 3D time-travel prototype. Our goal is to enable learners to explore India's sacred monuments in genuine 3D WebGL, understand the architectural marvels behind them, and connect each monument with the historical rulers and visionaries who commissioned them.

Built deliberately as a 1st-Year B.Tech Computer Science project, Virasat avoids bloated frameworks (React, Next.js, Redux, Tailwind) in favor of deep mastery of core web fundamentals: clean semantic HTML5, responsive CSS3 with CSS variables, asynchronous JavaScript (Promises/Fetch), and RESTful client-server routing in Node.js/Express.

💻 Technology Stack Breakdown

🌐

Frontend Core

HTML5: Semantic tags (<header>, <nav>, <main>, <article>, <section>).
CSS3: CSS Custom Properties (Variables), Flexbox, CSS Grid, and responsive breakpoints.
Vanilla JavaScript (ES6+): Async/await, fetch() API, DOM manipulation, input debouncing.

🧊

3D WebXR Engine

Google <model-viewer>: High-performance WebGL/WebXR web component.
Binary glTF (.glb): Industry-standard 3D asset format packaging geometries, PBR textures, and materials.
Camera Orbit & AR: 360-degree interactive rotation, zoom, auto-rotation, and mobile AR quick-look.

⚙️

Backend & REST API

Node.js: Fast asynchronous JavaScript runtime environment.
Express.js: Lightweight server delivering static assets and REST API endpoints.
REST Endpoints: /api/monuments, /api/monuments/:id, /api/figures, /api/figures/:id, /api/categories, /api/visual-search.

📷

Visual Search & Camera

MediaDevices API: Live device camera feed with facingMode: environment for mobile phones.
Canvas & FileReader APIs: In-memory frame capture, client-side RGB palette extraction, and drag-and-drop uploads.
Privacy & Integrity: Immediate camera track termination (track.stop()) and honest architectural matching without fake AI scores.

🏗️ System Architecture & Data Flow

Virasat follows a decoupled Client-Server REST Architecture:

🎓 College Viva Defense Guide (10 Questions & Answers)

Viva-Ready

These 10 questions and answers are written in clear, confident language tailored for a 1st-year B.Tech CS engineering viva examination:

Q1: What is Virasat, and what real-world problem does it address?

Answer: Virasat is an interactive 3D heritage exploration web platform. Most existing educational portals display static 2D images and dry text, making it difficult for students and tourists to appreciate architectural grandeur and cultural depth. Virasat solves this by combining interactive 3D reconstructions with historical context, architectural breakdowns, verified sources, and bidirectional links to the historical figures who built or defended these monuments.

Q2: Why did you choose Google <model-viewer> instead of raw Three.js or Unity WebGL?

Answer: While Three.js is powerful, writing a full WebGL camera controller, lighting setup, shadow casting, touch gesture handling, and responsive canvas sizing requires hundreds of lines of boilerplate that can introduce memory leaks. Google <model-viewer> is a standardized, production-grade Web Component built on top of Three.js. It gives us instant support for 360° mouse/touch orbit, auto-rotation, pinch-to-zoom, AR quick-look on mobile phones, and accessible fallback states with clean HTML semantics.

Q3: How does client-server communication work in this project?

Answer: We use the standard REST (Representational State Transfer) architectural pattern. The Node.js Express server exposes REST endpoints such as GET /api/monuments and GET /api/figures. The browser frontend uses the modern JavaScript fetch() API to make asynchronous HTTP requests. The server responds with structured JSON data, which the client parses and dynamically renders into HTML cards using DOM manipulation.

Q4: Why did you build Virasat in Vanilla JavaScript instead of React, Angular, or Next.js?

Answer: In first-year computer science, the goal is to master the foundational pillars of web engineering: semantic HTML, the CSS box model, asynchronous execution (Event Loop, Promises), and the Document Object Model (DOM). Using heavy frameworks introduces build systems (Webpack/Vite), transpilers (Babel), and virtual DOM overhead that obscure how the web really works. Vanilla JS ensures lightning-fast page loads, zero build dependencies, and code that is transparent and easy to explain during a viva.

Q5: How does the search and filter mechanism work in the Explore Dashboard?

Answer: We implemented a multi-dimensional search algorithm on the backend Express route (GET /api/monuments). It accepts query parameters for search, category, state, and unesco. The server converts search tokens to lowercase and checks across multiple fields: monument name, city, state, dynasty, architectural style, short description, and associated historical figures. Results are filtered and returned as a JSON array.

Q6: What is a .glb file, and how does the browser render it?

Answer: .glb is the binary container format of glTF 2.0 (GL Transmission Format), commonly referred to as the "JPEG of 3D". Unlike plain OBJ or STL files, a .glb file packages the complete 3D scene: 3D polygon meshes, vertex normals, material shaders (PBR: Physically Based Rendering), and embedded textures into a single compact binary file. The browser's WebGL graphics pipeline loads this directly into GPU memory for real-time 60 FPS hardware-accelerated rendering.

Q7: How are monuments and historical figures linked in your database?

Answer: We implemented a bidirectional normalized relational model in JavaScript. Each monument record in data/monuments.js contains an array of figure IDs (e.g., historicalFigures: ["shah-jahan", "mumtaz-mahal"]). Conversely, each figure record in data/figures.js contains an array of monument IDs (e.g., associatedMonuments: ["taj-mahal", "red-fort"]). In server.js, when a client requests a specific monument or figure by ID, the server automatically joins and resolves the linked records so the user can seamlessly navigate back and forth.

Q8: What is debouncing, and why is it used on the search input?

Answer: Debouncing is an optimization technique that limits how often a function is executed. If a user types "Taj Mahal" rapidly, an un-debounced input would fire 9 consecutive HTTP network requests to the server. By implementing a 250ms debounce with setTimeout() and clearTimeout(), the app waits until the user pauses typing before making a single fetch request, saving network bandwidth and server compute.

Q9: How do you handle monuments that do not yet have 3D models?

Answer: In academic prototypes, honesty is crucial. We never fake 3D models or show broken placeholders. Each monument has a boolean flag hasModel. For Taj Mahal and Ram Mandir, hasModel is true and the interactive <model-viewer> is rendered. For the remaining monuments, our frontend gracefully displays an honest banner: "3D Digital Twin Under Photogrammetry Reconstruction" while keeping all historical facts, architecture details, and academic citations fully accessible.

Q10: What are the next technical enhancements planned for Virasat?

Answer: Planned future enhancements include:
1. Connecting SQLite or PostgreSQL with Prisma for persistent user bookmarking and community photo submissions.
2. Adding interactive 3D annotations (hotspots) directly on <model-viewer> so clicking a dome or minaret reveals micro-history cards.
3. Offline caching with a Service Worker (Progressive Web App - PWA) so students in low-connectivity areas can explore heritage offline.

Q11: How does the Camera and Visual Search feature work, and how do you handle privacy and permissions?

Answer: Visual Search uses the browser's native navigator.mediaDevices.getUserMedia() API with facingMode: { ideal: "environment" } to prioritize rear mobile cameras. To respect user privacy:
1. The camera is never opened automatically; access is requested only when the user explicitly clicks the camera button.
2. All camera video tracks are immediately stopped via stream.getTracks().forEach(t => t.stop()) when the user captures a frame or closes the modal, turning off the device camera light.
3. If permissions are denied or the device lacks a webcam, a friendly fallback immediately guides the user to the file upload tab (which supports <input type="file" accept="image/*" capture="environment">).
4. Photographs are processed transiently in memory using the HTML5 Canvas API (for RGB palette analysis) and are never permanently stored on the server.
5. Catalogue candidate matching is explainable and honest: candidates are ranked by architectural category, materials, and user clues rather than fabricating black-box neural network percentages.
